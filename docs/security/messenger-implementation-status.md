# Messenger implementation status

Phase 0 and Phase S are done except the items listed at the end. **Nothing here is end-to-end encrypted yet**: chats are sealed at
rest with a server-held key (`docs/guides/encryption.md`), which protects a database dump, not a compromised server.

## Done and verified

- One runtime store for channels, pairs, hosted workers and observers; agents in groups are woken, reply, and stay silent on `[PASS]`.
- Membership-based chats with human and agent members, stable tenant-aware direct-chat ids, admin roles, tenant-scoped access
  (404 across tenants, RFC 9457 errors), real edit, delete and reactions, files, read and delivered cursors, `read_by_all`.
- A durable feed that catches up after a disconnect and revokes removed members mid-stream; **Redis fan-out verified between two
  server processes** (`TEST_REDIS_URL=redis://... pytest -k redis`, polling raised to 30 s so only Redis can deliver).
- **Typing**: an ephemeral 5-second hint (Redis across processes, memory otherwise), shown with the person's roster name; never stored.
- **Receipts**: per-person seen, delivered and waiting, as a tooltip and a tick in the console; the chat list names who spoke last.
- Organization people search and invites (scoped to the caller's org), people picker, direct conversations, bot badges, and the
  "AI agents and their providers can read this chat" notice.
- **Two real users in two browsers** (demo and bea, same org): create a group, receive each other's messages live, see typing, and
  see "Seen by Bea Tester".
- **At-rest sealing** of chat text and card data (AES-256-GCM, per-chat HKDF keys, field-bound, key ring for rotation) and of the
  workspace and connector OAuth tokens; a database scan test finds no plaintext. Keys are generated by `gen-env.sh` and the Helm chart.
- PWA manifest and service worker (only a public offline page is cached), optional VAPID push with a content-free wake.
- Nonce CSP on chat pages. **XSS corpus** (19 payloads through the group Markdown, the main chat bubble, A2UI cards and OpenUI pages,
  plus a control proving the check can fail): no script, frame, handler or javascript:/data: address reaches the page.
- Trusted Types: our own code has **zero** violations (the service-worker registration goes through a policy that allows only our
  worker). The policy is still report-only.

## Open before Phase 0 and S are complete

- **Trusted Types enforcement.** The remaining report-only violations are framework code in the dev build (Next's script loader,
  React's server-DOM runtime, zod's code generation). Measure a production build, add a default policy or fix those sinks, then enforce.
- **Browser push against a real push service** and Lighthouse installability (tests use a mock push service).
- **Sealing keys wrapped by the organization's KMS** (today they come from the environment); sealing of the 1:1 run log is not done
  because the server searches and summarises it (disk encryption covers it).
- Atomic catalog/runtime membership transitions under concurrent admin changes; agent media/sandbox parity checks for group agents.
- Delete chat sealing for rows written before keys were set (they stay readable and are sealed on their next write).

## Encryption gate

No MLS code, keyholder, recovery, cross-signing, retention archive, safety numbers or audit exists. The threat model and E1 design in
this folder have been reviewed (see `e1-design.md`, "Review notes"). Never turn the `e2ee` flag on to represent encryption that does not exist.
